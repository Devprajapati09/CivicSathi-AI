1. Executive Summary
CivicSathi AI is a hackathon prototype that helps citizens report potholes, garbage accumulation, broken streetlights, and waterlogging. A citizen uploads a photo and types an area name. The app analyzes the image using a pretrained vision model when configured, looks up a ward and department from local mock data, asks the citizen to confirm, creates a persistent ticket, and later answers status questions using the saved record.
This PRD is optimized for a strict three-hour build in Google Antigravity. No custom model training, real AMC integration, complex maps, login system, or notification integrations are required. The municipal workflow is simulated locally and must be labelled as demo data.
2. Problem and Product Goal
Problem: people often give up reporting civic issues because they must identify the correct ward and department, file a complaint, and repeatedly follow up.
Goal: reduce this effort to a short photo-and-area workflow, then provide a real local tracking ID and status lookup.
Success in the demo means
Upload/select a sample photo and show a preview.
Return live vision analysis if configured, otherwise clearly label the selected demo scenario.
Map a known typed area to a mock ward and department.
Require citizen confirmation before ticket creation.
Persist a unique ticket ID in local JSON.
Retrieve the saved status by ID and reflect admin status changes.
Show the agent’s steps in the UI rather than only a generic chatbot response.

6. USP — What Makes It Different
Primary USP: Evidence-to-Action Civic AI
Instead of merely classifying a photo, CivicSathi turns the photo and area into a structured, trackable complaint using a sequence of tools.
USP 1 — Duplicate Complaint Intelligence (best optional feature)
Before ticket creation, search unresolved local tickets for the same issue category and area. Show a possible match and its ticket ID. Let the citizen continue with a new ticket or refer to the existing one. Never automatically reject a complaint.
USP 2 — Explainable Civic Impact Score (stretch)
If the core flow is complete, calculate a prototype score from 0–100 using visible severity (0–40), potential safety risk (0–40), and similar reports (0–20). Explain the components and label it a demo estimate, not an official AMC priority.
USP 3 — Real Status, Not a Fake Chatbot
The status assistant must retrieve the saved ticket from JSON. Demonstrate a status update and then ask for the status again.
Three-hour rule: implement the primary workflow first; duplicate checking is the one recommended USP. Impact scoring is optional.

10. Minimal Architecture
React UI  -> Express API      -> analyzeIssueImage()  [vision API or labelled demo mode]      -> lookupWardDepartment() [local JSON]      -> detectDuplicates() [optional]      -> createComplaintTicket() [local JSON]      -> getComplaintStatus() [local JSON]
The browser must not read or write JSON files directly. All persistence and API secrets stay on the backend.

15. Acceptance Checklist
Frontend and backend start with documented commands.
Photo can be selected and previewed; invalid files are rejected.
Live analysis is labelled live; fallback is labelled demo.
Known area maps to seeded mock ward; unknown area is not fabricated.
No ticket is created before confirmation.
Ticket ID is unique and the saved ticket survives a server restart.
Valid ID returns the actual status; unknown ID returns not found.
Admin status change, if implemented, is reflected in the next status query.
Possible duplicate is a suggestion and never blocks a citizen automatically.
AI/storage failure does not produce a false success message.

17. Security and Limitations
Store AI API keys only in backend .env; add .env to .gitignore and provide .env.example.
Validate image MIME/type and size; do not trust file extensions alone.
Do not expose stack traces, API keys, or arbitrary file paths.
Use mock ward mappings and label them as demonstration data.
AI image analysis and severity can be wrong; let the citizen correct the result.
Impact score is an illustrative rule, not official policy.
JSON storage is for a small local single-process demo only.
No actual complaint is submitted to AMC.

19. Definition of Done
The build is complete when a judge can select or upload a photo, enter a known area, review live or clearly labelled demo analysis, confirm the complaint, receive a unique locally persisted ticket ID, and retrieve the saved status. Duplicate detection is the recommended differentiator only after this path works.
